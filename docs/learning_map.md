# 学习地图：从项目反推知识点

> 用法：按项目的开发顺序，一个节点一个节点地学。每个节点先打开对应文件看代码，再学知识点，最后做“自测题”和“动手改一处”。
> **过关标准：自测题能不看代码讲出来，动手题能独立改完并跑通。** 面试官问的就是这些。
>
> 优先级：**P0 = 必须会（面试一定问）**，P1 = 加分项，P2 = 了解即可。

## 学习顺序和时间（按每天 8 小时）

| 周 | 学习内容 | 对应节点 | 同时做 |
|---|---|---|---|
| 第 1 周 | SQL（重中之重）+ 数据分析思维 | 节点 1、2、3 | 每天 10 道 SQL 题；周末开始投简历 |
| 第 2 周 | Python 基础巩固 + 看板 + 大模型 API | 节点 4、5 | 每天投 10–20 份 |
| 第 3 周 | RAG、工作流、评测 + 面试表达 | 节点 6、7、8 | 模拟面试（见 interview_qa.md） |

> 不用等学完再投简历。第 1 周末就可以投，边面试边补短板，面试里被问倒的问题就是下一步要学的。

## 节点 1：数据接入与存储

**做了什么**：3.5GB CSV 转成 Parquet，用 DuckDB 查询。
**对应文件**：`pipeline/build_warehouse.py`（`build_ods` 函数）、`pipeline/db.py`、`config.py`

| 优先级 | 知识点 | 说明 |
|---|---|---|
| P0 | CSV 与 Excel 的区别 | 为什么 1 亿行不能用 Excel 打开（Excel 最多约 104 万行） |
| P0 | 数据库是什么、表 / 行 / 列 / 字段类型 | INTEGER、VARCHAR、DATE、TIMESTAMP |
| P1 | 行式存储 vs 列式存储 | Parquet、DuckDB 为什么查询快：分析时只读需要的列 |
| P1 | OLTP vs OLAP | MySQL 管交易（增删改），DuckDB / ClickHouse / Hive 管分析（大量汇总查询） |
| P1 | 内存不够怎么办 | DuckDB 的 memory_limit 和临时目录（溢出到硬盘） |
| P2 | Python 虚拟环境、requirements.txt、.env | 为什么密钥不能写进代码、不能提交到 Git |

**自测题**
1. 3.5GB 的 CSV 转成 Parquet 后只有 650MB，为什么？
2. 为什么这个项目用 DuckDB，不用 MySQL？
3. `.gitignore` 里为什么要写 `data/` 和 `.env`？

**动手改一处**：在 `config.py` 里把 `DUCKDB_MEMORY_LIMIT` 改成 `2GB`，重新运行 `python pipeline/build_warehouse.py`，记录用时变化。

## 节点 2：数据清洗（DWD 层）

**做了什么**：剔除时间范围外的数据、去重、时间戳转北京时间。
**对应文件**：`sql/01_dwd_user_behavior.sql`

| 优先级 | 知识点 | 说明 |
|---|---|---|
| P0 | `SELECT / WHERE / DISTINCT / IN / BETWEEN` | 最基础的筛选 |
| P0 | 常见脏数据类型 | 缺失值、重复值、异常值（时间越界）、格式不一致 |
| P0 | 时间戳和时区 | Unix 时间戳是 UTC 秒数，北京时间 = UTC + 8 小时 |
| P1 | CTE（`WITH ... AS`） | 把复杂 SQL 拆成几步，可读性高 |
| P1 | 清洗要“留痕” | 剔除了多少、为什么剔除，要能说清楚（见 `reports/data_quality.md`） |

**自测题**
1. 你怎么发现数据里有脏数据的？剔除了多少条？会不会影响结论？
2. 为什么时间戳要加 28800？
3. `DISTINCT` 和 `GROUP BY` 去重有什么区别？

**动手改一处**：在 `quality_checks.py` 里加一条检查：“DWD 表里每天至少有 900 万条记录”。

## 节点 3：数仓分层与指标计算（DWS / ADS 层）⭐ 最重要

**做了什么**：明细 → 用户 / 商品 / 品类汇总 → 日指标、漏斗、留存、复购、RFM。
**对应文件**：`sql/03_dwd_order.sql`、`sql/04_dws.sql`、`sql/05_ads.sql`

| 优先级 | 知识点 | 说明 |
|---|---|---|
| P0 | `GROUP BY` + 聚合函数 | `COUNT / SUM / AVG / MIN / MAX`，`COUNT(DISTINCT)` |
| P0 | `JOIN`（INNER / LEFT） | 什么时候用 LEFT JOIN（例：没下过单的用户也要保留） |
| P0 | **窗口函数** | `ROW_NUMBER / RANK / LAG / SUM() OVER()`，面试第一轮必考 |
| P0 | `CASE WHEN` | 分组打标签（RFM 分层就是用它） |
| P0 | 电商核心指标 | PV、UV、日活、GMV、订单数、付费率、转化率、客单价、复购率、留存率 |
| P0 | **指标口径** | 同一个“转化率”，次数口径 2.2%，用户口径 61%，必须先说清口径 |
| P0 | 漏斗分析、RFM 模型 | 能讲清步骤定义、阈值怎么定、每类人群怎么运营 |
| P1 | 数仓分层 ODS / DWD / DWS / ADS | 为什么分层：复用、口径统一、查询快、出错好排查 |
| P1 | `FILTER` 子句、`arg_max` | DuckDB 的便捷写法；换成 MySQL 要改成 `SUM(CASE WHEN ...)` |
| P1 | 中位数 vs 平均数 | 消费金额是长尾分布，平均数被大户拉高，所以 RFM 阈值用中位数 |

**自测题**
1. 漏斗为什么要“逐级包含”？不包含会出现什么问题？
2. RFM 的 F 为什么用“购买天数”而不是“购买次数”？
3. 用窗口函数写：每天 GMV 排名前 3 的品类。
4. 为什么要先建 `dws_user_daily` 再算日活和留存，而不是直接从 1 亿行明细算？

**动手改一处**：在 `05_ads.sql` 里新增一张表 `ads_category_daily_top3`：每天 GMV 前 3 的品类（用 `ROW_NUMBER() OVER (PARTITION BY dt ORDER BY gmv DESC)`）。

**练习资源**：牛客网 SQL 必知必会 + SQL 进阶题、LeetCode 数据库题（简单 + 中等）。每天 10 道，坚持 2 周。

## 节点 4：数据分析与解读

**做了什么**：从数字里得出结论，并识别数据陷阱。
**对应文件**：`docs/analysis_report.md`、`tools/export_dashboard_data.py`（各页“关键发现”的计算）

| 优先级 | 知识点 | 说明 |
|---|---|---|
| P0 | 环比、同比、占比、增长率 | 周末要和上周末比，不能和工作日比 |
| P0 | 异常值识别 | 留存在 12-02 跳到 98%：先怀疑数据，再下结论 |
| P0 | 分析报告结构 | 结论先行：结论 → 数据支撑 → 原因推测 → 建议 |
| P1 | 相关 ≠ 因果 | “加购的人更容易买”不代表“让人加购就会买” |
| P1 | A/B 测试基础 | 想验证“购物车提醒有没有用”，要分实验组和对照组 |
| P1 | 帕累托 / 长尾 | 5.6% 的品类贡献 80% 的 GMV |

**自测题**
1. 周末日活涨了 36%，你会怎么判断这是好事还是数据问题？
2. 如果老板问“转化率是多少”，你怎么回答？
3. 你给出的 5 条建议里，哪一条最优先？怎么验证效果？

**动手改一处**：给“经营总览”页的“关键发现”加一条你自己的发现（改 `tools/export_dashboard_data.py` 里 `overview()` 的 `findings` 列表，再运行一次 `python tools/export_dashboard_data.py`）。

## 节点 6：AI 问数（Text-to-SQL）⭐ AI 岗必问

**做了什么**：中文问题 → 大模型写 SQL → 安全检查 → 执行 → 出错自动修正 → 总结。
**对应文件**：`ai/llm.py`、`ai/schema.py`、`ai/text2sql.py`、`eval/run_text2sql_eval.py`

| 优先级 | 知识点 | 说明 |
|---|---|---|
| P0 | 大模型 API 调用 | messages（system / user / assistant）、temperature、max_tokens、API Key |
| P0 | Prompt 工程 | 角色、上下文（表结构）、规则、输出格式、示例 |
| P0 | 结构化输出 | 让模型返回 JSON，代码再解析 |
| P0 | **语义层** | 模型不认识你的表，表和指标的说明写得越清楚越准（`ai/schema.py`） |
| P0 | 安全 | 只读连接 + 只允许 SELECT + 超时 + 行数限制，防止 AI 删库 |
| P1 | 自我修正（Self-correction） | 把报错发回给模型重写，最多 2 次 |
| P1 | **评测** | 执行准确率：比结果不比写法；分题型统计错在哪 |
| P1 | 多轮对话 | 把上一轮问题和 SQL 带进去，支持追问 |
| P2 | Few-shot、相似问题检索 | 改进准确率的下一步 |

**自测题**
1. 你的 AI 问数准确率多少？怎么测的？错的题错在哪？
2. 如果 AI 生成了 `DROP TABLE`，你的系统会怎样？（三层防护）
3. temperature 为什么设成 0？
4. 模型怎么知道“复购率”怎么算？

**动手改一处**：在 `eval/text2sql_cases.json` 加 3 道你自己出的题，重跑评测，看准确率变化。

## 节点 7：自动周报与工作流

**做了什么**：SQL 算数 → 模型写分析 → 数字核对 → 飞书推送；n8n 每周一自动触发。
**对应文件**：`ai/weekly_report.py`、`api/server.py`、`workflows/n8n_weekly_report.json`

| 优先级 | 知识点 | 说明 |
|---|---|---|
| P0 | “大模型不算数” | 数字由 SQL 算，模型只写字；再用代码核对文中数字（防幻觉） |
| P0 | HTTP 接口基础 | GET / POST、JSON、状态码；用 `/docs` 页面测试接口 |
| P0 | n8n 基本概念 | 触发器（定时 / Webhook）→ 节点 → 条件分支 → 输出 |
| P1 | FastAPI | 路由、参数、请求体（Pydantic） |
| P1 | Webhook | 飞书机器人就是一个 Webhook 地址，POST 一段 JSON 就能发消息 |
| P1 | 兜底设计 | 模型调用失败自动改用模板，保证周报一定发出 |
| P2 | Docker | n8n 一般用 Docker 运行；`host.docker.internal` 是容器访问宿主机的地址 |

**自测题**
1. 周报里如果模型编了一个数字，你的系统怎么发现？
2. 为什么 n8n 不直接连数据库，而是调用你的接口？
3. 定时任务失败了怎么办？

**动手改一处**：在 n8n 里导入工作流，把触发时间改成每天 9 点，并成功推送一次到你自己的飞书群。

## 节点 8：智能客服（RAG）与工单分类

**做了什么**：规则文档切片 → 检索 → 只根据资料回答 + 标注来源；工单 8 分类，规则法 vs 大模型对比。
**对应文件**：`ai/rag.py`、`ai/tickets.py`、`kb/`、`eval/run_service_eval.py`、`docs/dify_guide.md`

| 优先级 | 知识点 | 说明 |
|---|---|---|
| P0 | RAG 原理 | 为什么要检索：模型不知道你的店铺规则，直接问会编 |
| P0 | 切片（Chunking） | 按小节切，每段带标题；切太大噪音多，切太小上下文不够 |
| P0 | 关键词检索 vs 向量检索 | BM25 认字面（“内裤”搜不到“贴身衣物”），向量认语义；实际常用混合检索 |
| P0 | 拒答 / 转人工 | 检索分数太低就不让模型回答，避免编造 |
| P0 | Dify 的知识库和工作流 | 和你以前做过的工单 RAG 对应起来讲 |
| P1 | Embedding、向量数据库 | 文本 → 向量，余弦相似度；Milvus、Chroma、pgvector |
| P1 | RRF 融合、重排序（Rerank） | 两路检索结果怎么合并 |
| P1 | 检索评测 Hit@K、回答评测 | 先看检索对不对，再看回答对不对 |
| P1 | 分类任务评测 | 准确率、混淆（哪类容易分错）、规则基线 vs 模型 |
| P2 | 过拟合评测集 | 同义词表在评测集上调过，所以分数偏乐观，需要独立测试集 |

**自测题**
1. RAG 的完整流程是什么？每一步可能出什么问题？
2. 顾客问“内裤拆了能退吗”，为什么关键词检索一开始搜不到？你怎么解决的？
3. 你的检索准确率 100%，可信吗？
4. 什么情况下转人工？

**动手改一处**：在 `kb/docs/` 新增一篇《预售规则》，加 2 道评测题，重跑 `python eval/run_service_eval.py`。
