# 面试准备：项目介绍 + 高频追问

> 参考答案是“要点”，不要背原文，用自己的话讲。讲不出来的题，回到 learning_map.md 对应节点补。

## 一、1 分钟项目介绍（背熟）

> 我做了一个“电商 AI 运营助手”项目，用的是阿里天池 1 亿条淘宝用户行为数据。
> **数据部分**：我用 DuckDB 把 3.5GB 原始数据分成 ODS、DWD、DWS、ADS 四层，清洗了时间越界和重复数据，建了 16 项自动质量检查；在此基础上做了经营总览、用户漏斗、RFM 分层、品类四象限四个分析页面。比如我发现 79% 的购买用户都加购过商品，所以建议把“加购未购买”作为优先转化对象；还发现留存在 12 月 2 日突然跳到 98%，判断是数据抽样问题，没有直接用。
> **AI 部分**：做了三个功能。一是 AI 问数，业务用中文提问，大模型写 SQL 在只读库执行，用 23 道标准题评测准确率；二是自动周报，数字全部由 SQL 计算，模型只写分析，并且自动核对文中数字防止编造，用 n8n 每周一推送到飞书；三是智能客服，用 RAG 检索店铺规则回答问题，查不到就转人工，同时做工单自动分类。
> 这个项目让我把数据分析和 AI 落地串成了一个完整流程。

## 二、数据分析类

**1. 数据清洗你做了哪些？怎么证明清洗是对的？**
要点：时间越界 55,576 条（1901 年、2037 年这种时间戳）、完全重复 49 条、只保留 4 种行为；剔除比例 0.06%，不影响结论。用 16 项质量检查证明：空值为 0、主键唯一、订单表行数 = 明细购买行数、各层汇总能对上、漏斗逐级递减等，结果写在 `reports/data_quality.md`。

**2. 为什么要分 ODS / DWD / DWS / ADS？**
要点：ODS 保留原始数据，出问题可以回溯；DWD 统一清洗规则，后面所有指标同一口径；DWS 先聚合到“用户 × 天”等粒度，把 1 亿行压到几百万行，后面查询快；ADS 直接给看板和 AI 用。好处：口径统一、复用、性能、好排查。

**3. 转化率是多少？**
要点：先问口径。次数口径（订单 ÷ 浏览）2.2%；用户口径（购买用户 ÷ 浏览用户）61%。前者看流量效率，后者看用户最终有没有买。

**4. RFM 怎么做的？阈值怎么定？**
要点：R = 最近一次购买距 12-04 天数，F = 购买天数，M = 消费金额。R、M 用付费用户中位数做阈值（金额长尾，平均数会被大户拉高），F 以 2 天为界（复购）。8 类人群。数据只有 9 天，所以用高 / 低两档；真实业务一般用 1–3 个月数据、五分位打分。

**5. 你的分析有什么局限？**
要点：只有 9 天；价格是模拟的；数据是抽样的（留存异常就是证据）；只能看相关不能证明因果，建议需要 A/B 测试验证。

**6. 留存为什么在 12-02 跳到 98%？**
要点：这两天日活比前一周同期多约 35%，几乎所有用户都出现，更像抽样方式（抽取在这段时间内有行为的用户）或大促预热导致。处理：评估留存只用 11-25 至 11-30 的次日留存（78%–80%）。原则：好得不正常的数字先怀疑数据。

**7. 现场 SQL：每天 GMV 前 3 的品类**
```sql
SELECT * FROM (
  SELECT dt, category_id, gmv,
         ROW_NUMBER() OVER (PARTITION BY dt ORDER BY gmv DESC) AS rn
  FROM dws_category_daily
) WHERE rn <= 3;
```
追问 `ROW_NUMBER / RANK / DENSE_RANK` 的区别：并列时 ROW_NUMBER 不并列；RANK 并列后跳号（1,1,3）；DENSE_RANK 不跳号（1,1,2）。

**8. 现场 SQL：次日留存率**
要点：用户 × 天的活跃表自关联，`b.dt = a.dt + 1`，按 a.dt 分组，留存人数 ÷ 当天活跃人数。

## 三、AI 应用类

**9. AI 问数的流程？**
要点：拼提示词（表结构说明 + 业务口径 + SQL 规则）→ 模型返回 JSON（SQL + 思路）→ 安全检查 → 执行 → 报错就把错误信息发回去让模型修，最多 2 次 → 结果交给模型写结论。

**10. 准确率多少？怎么评测？**
要点：23 道标准题，分基础指标、时间筛选、排名、口径、复杂查询、拒答、安全 7 类。用执行准确率：比较执行结果而不是 SQL 写法（同一问题很多种写法）。说出具体数字和错题原因（评测完填到 `reports/text2sql_eval.md`）。

**11. 怎么防止 AI 删库？**
要点：三层。① 数据库只读连接；② 代码检查只允许单条 SELECT，拦截 DROP / DELETE / ATTACH / 读文件函数等；③ 30 秒超时 + 最多返回 500 行。

**12. 怎么提高准确率？**
要点：语义层写清楚（每张表的粒度、每个指标的口径）、让模型优先用汇总表、错误自动修正；下一步做 few-shot：把相似的历史问题和正确 SQL 检索出来放进提示词。

**13. 周报怎么防止模型编数字？**
要点：职责分离——数字全部由 SQL 计算，模型只负责写字；生成后用代码提取文中所有数字，和 SQL 结果比对，对不上的标红；n8n 里加条件分支：核对不通过就不发群，改发提醒让人工审核。模型调用失败自动用模板兜底。

**14. RAG 的流程？你遇到过什么问题？**
要点：切片（按小节、带标题）→ 检索（BM25，可选向量混合，RRF 融合）→ 拼提示词（只根据资料回答、标注来源）→ 生成。问题：顾客说“内裤拆了能退吗”，文档写的是“贴身衣物”，关键词检索搜不到。解决：加同义词扩展；根本解决是用向量检索理解语义。另外设置分数阈值，查不到就不调用模型、直接转人工。

**15. 检索准确率 100%，可信吗？**
要点：不完全可信。同义词表是对着评测题调的，存在过拟合；评测集也是我自己写的。需要用真实工单做独立测试集。（主动说出局限比被面试官戳穿好得多。）

**16. 工单分类为什么要用大模型？规则不是 93% 吗？**
要点：规则和工单都是我写的，偏乐观；规则遇到组合诉求就错，比如“有人让我提供验证码退款”被规则判成退款，其实是账户安全。大模型能理解主要诉求，还能同时输出紧急程度、情绪、摘要。成本上可以先规则、规则判不了再用模型。

**17. 你用过 Dify 吗？和你自己写的有什么区别？**
要点：用过，做过客服工单 RAG（见 `docs/dify_guide.md`）。Dify 适合快速搭原型、非技术同事也能维护；代码版更灵活：可以自定义检索策略、做评测、接进自己的系统。实际工作中两者结合：Dify 编排，复杂能力做成接口给 Dify 调用。

**20. 项目里最难的是什么？**
